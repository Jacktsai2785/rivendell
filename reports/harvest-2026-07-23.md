## 二、Skill 候選

### 🟢 Strong：`review-staged`（commit 前 staged 審查閘門）

- **名稱**：`review-staged`（建議放 `quality/`）
- **目的**:一鍵執行「只審 `git diff --cached`、只列 CONFIRMED / 高信心 correctness 問題」的 `/code-review xhigh`，把目前每次手打的長參數固定成 skill 內建規則。
- **觸發**：「審查 staged」「commit 前檢查」「review staged」，或準備 commit 前主動建議。
- **類別**：quality / git
- **理由**：**5 個 session 參數逐字相同**，是本批最強的重複訊號。手動貼參數有打錯或漏規則的風險；codify 後規則保證一致，還可加上「無 staged 變更時提前中止」的防呆。現有 skills 中無任何 staged-only review 包裝（`/code-review` 是通用指令、`project-redteam-review` 是全專案盤點、gstack 的 `review` 是另一體系）。

### 🟢 Strong：`review-prepush`（推送前 commit range 審查）

- **名稱**：`review-prepush`
- **目的**：自動計算即將推送的範圍（`@{upstream}..HEAD`，無 upstream 則 fallback 問使用者），再以同一套 CONFIRMED-only 規則跑 `/code-review xhigh`。
- **觸發**：「推送前審查」「review 這次要 push 的」「pre-push review」。
- **類別**：quality / git
- **理由**：出現 3 次，且目前流程要**使用者手動查兩個 SHA 貼進參數**——這正是最該自動化的部分（`git rev-parse @{u}` 一行可解）。可與 `review-staged` 合併為單一 skill 的兩種模式（`--staged` / `--push`），我傾向合併，維護成本較低。

### 🟡 Moderate：無獨立候選，但有一個流程觀察

staged 審查連續出現 5 次、間隔很短,代表使用者正在以「每次 commit 前必審」的紀律工作。若上面 Strong 候選落地後仍嫌手動,下一步可考慮升級為 **PreToolUse/pre-commit hook 自動觸發**(類似現有 `auto-stage` 的 hook 形式)。但目前證據只支撐「手動一鍵化」,hook 化建議等 skill 用過幾週再評估,故不列為獨立候選。

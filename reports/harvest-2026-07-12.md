## 二、Skill 候選清單（已排除既有 skill 重疊者）

### 🟢 Strong

#### 1. `skill-catalog-drift-sync`
- **目的**：自動比對「磁碟上的 skills 實際目錄結構」與「rivendell 前端 `playbook-data.ts` / 顯示層」的差異，偵測搬移、改名、刪除造成的路徑漂移，直接產出修正 diff。
- **觸發**：搬移或整併 skill 目錄後；使用者說「前端顯示跟實際不符」「skill 路徑錯了」「找漂移」；或作為 commit 前檢查。
- **分類**：meta
- **理由**：Session 8+9 合計 98 則訊息、66 次 Bash，全在做這件事的人工版。既有的 `sync-readme` 只同步 README，`doc-drift-sync` 針對 CHANGELOG/ROADMAP 文件，都不覆蓋「skill 目錄 ↔ 前端資料檔」這條軸線。這是 skill-lab 架構下必然反覆發生的維運工作（gstack 才剛搬進來一次就炸了）。

#### 2. `service-watchdog-systemd`
- **目的**：`1-service-watchdog-launchd` 的 WSL2/Linux 版——為 rivendell 等 HTTP 服務建立 systemd unit + HTTP probe + 自動重啟，並涵蓋「整個壞掉了」時的診斷 → 復原 SOP。
- **觸發**：「rivendell 壞掉了」「服務又掛了」「開機自動啟動」，或在 Linux/WSL 環境觸發 watchdog 需求。
- **分類**：workflow
- **理由**：既有 watchdog skill 明確綁定 macOS launchd，但使用者目前主力環境是 WSL2（本 session 環境即是）。Session 10 已手工產出 `rivendell-systemd-services.md`，等於素材現成，只差包成 skill。多裝置使用下這問題會再發生。

#### 3. `claude-env-sync`
- **目的**：跨裝置同步 Claude Code 環境——盤點 `~/.claude/`（settings、skills、hooks、memory、plugins）哪些該同步、哪些是裝置特定（settings.local.json、快取），產出 git-based dotfiles 同步方案與新機 bootstrap 腳本。
- **觸發**：「兩台裝置環境同步」「新電腦要設定 claude」「把我的環境搬過去」。
- **分類**：meta
- **理由**：Session 12 直接問了這題，session 16 就是在第二台裝置上重建環境的實例。skill-lab 本身已是「skills 用 repo 管理」的雛形，缺的是把 settings/hooks/memory 一起納入的完整同步 SOP。現有清單無任何 skill 覆蓋。

### 🟡 Moderate

#### 4. `git-hooks-review-installer`
- **目的**：把審查邏輯（lint、secret 掃描、headless Claude review）打包成可安裝的 pre-commit / pre-push hooks 套件，一鍵 `install.sh` 部署到任意 repo。
- **觸發**：「commit 前自動檢查」「裝 pre-commit hook」「讓 agent 在 push 前把關」。
- **分類**：git
- **理由**：Session 13 花了 80 則訊息從零打造 `install.sh` + `lib-review.sh` + `pre-commit` + `pre-push`，成品已存在，值得固化成可重複安裝的 skill。評為 Moderate 是因為目前只發生一次，且與 `auto-stage`（PostToolUse hook）、`dev-process-gate` 概念相鄰，需要先釐清邊界避免疊床架屋。

#### 5. `mcp-plugin-doctor`
- **目的**：診斷 MCP server / plugin 連線失敗——檢查 plugin manifest 的 MCP url、認證狀態、`/mcp` 錯誤訊息，判斷是設定錯、plugin 版本問題還是該停用，並給出修復或降級步驟。
- **觸發**：「MCP 連不上」「plugin 一直 reconnect 失敗」「invalid MCP url」。
- **分類**：workflow
- **理由**：Session 15 的 `bio-research:benchling` 排障是純手工 Bash 摸索。安裝的 plugin 越多這類故障越常見。評為 Moderate 因目前僅一例，且部分情境可由官方 `/mcp` 指令自助。

#### 6. `api-preflight-probe`
- **目的**：新專案動工前，先用 curl 系統性實測外部 API（端點可達性、認證、rate limit、回傳 schema 快照），產出一份「API 可行性報告」再進骨架開發，避免蓋到一半發現資料源不可用。
- **觸發**：SPEC 中列有外部 API 依賴的新專案 init 階段；「先確認 API 能不能用」。
- **分類**：workflow
- **理由**：Session 11（twstock）明確採用「先實測 TWSE OpenAPI + FinMind、再建骨架」的順序，是個值得固化的好習慣，可掛在 `init-project` / `task-brief` 執行階段之後。評 Moderate 因單次出現，且與 `repro-exam`、`env-doctor` 有部分概念重疊。

### 🔴 Weak

#### 7. `permission-prompt-doctor`
- **目的**：診斷「白名單設好了為什麼還一直跳 yes」——比對 settings.json / settings.local.json 的 pattern 語法、scope 優先序、session 是否需重啟。
- **觸發**：「為什麼還要我按 yes」「allowlist 沒生效」。
- **分類**：meta
- **理由**：Session 14 是真實痛點，但 `setup-permissions`、`settings-audit`、`audit-fix`、內建 `fewer-permission-prompts` 已覆蓋大部分面向。建議做法是把「診斷不生效」章節**補進既有 `settings-audit`**，而非新建 skill。

#### 8. `gate-compliance-retro`
- **目的**：定期稽核 sessions，檢查 task-brief 等強制 gate 是否被實際遵守，未遵守時回報並強化規則。
- **觸發**：workflow retro 時、使用者質疑「你剛剛有走流程嗎」。
- **分類**：meta
- **理由**：Session 9、11 出現兩次質問，痛點真實；但機制上更適合併入既有的 `workflow-retro` 或 `session-harvest` 作為一個檢查項，獨立成 skill 價值有限。

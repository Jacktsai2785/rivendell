## 二、Skill 候選

### 🟡 Moderate — `browser-extension-review`

- **名稱：** browser-extension-review
- **目的：** 針對 Chrome/Firefox Extension（MV3）的專屬 code review 檢查清單：manifest permissions 最小化、host_permissions 範圍、content script 的 DOM 注入與 XSS 面、background↔content message passing 驗證、CSP、儲存敏感資料的位置。
- **觸發：** 「審查這個插件」「review extension」、diff 內含 `manifest.json` + `content.js`/`background.js` 時的 code review。
- **分類：** quality
- **理由：** 兩場 session 都在對同一個插件做審查，且通用的 `engineering:code-review` 不含插件特有檢查點。listen-web 是進行中的網頁朗讀插件專案，後續審查會反覆發生。**扣分：** 目前只在單一專案出現，可再觀察一輪；若下次審查仍手動補插件檢查點，即應建立。

### 🟡 Moderate — `brief-driven-review`（brief 對照驗收）

- **名稱：** brief-driven-review
- **目的：** code review 時強制先讀專案的 `BRIEF.md`（task-brief 五欄位產出），把「完成定義」與「邊界」轉成驗收清單，審查結論須逐項對照 brief 判定符合/偏離，而非只看程式碼品質。
- **觸發：** 專案根目錄存在 `BRIEF.md` 且使用者要求 review / 驗收 / 「做完了嗎」。
- **分類：** quality（或作為 task-brief 的下游配套）
- **理由：** Session 1 明確出現「讀 BRIEF.md → 審查實作」的順序，這是使用者 task-brief 工作流的自然延伸，且現有 skills（task-brief、dev-process-gate、engineering:code-review）都沒有把 brief 當驗收基準的環節。**扣分：** 也可以選擇不建新 skill，改為在 task-brief 或 dev-process-gate 內加一節「驗收模式」，避免 skill 碎片化。

### 🔴 Weak — `wsl-cli-tool-install`

- **名稱：** wsl-cli-tool-install
- **目的：** 在 WSL2 上安裝雲端/開發 CLI（gcloud、aws、az…）的標準流程：apt repo + GPG key 設定、PATH 寫入、認證初始化、WSL 特有陷阱（瀏覽器 OAuth 跳轉需 `--no-launch-browser`）。
- **觸發：** 「裝 gcloud」「install XX CLI」。
- **分類：** workflow
- **理由：** 僅出現一次、7 個 Bash 指令即完成，屬於一次性瑣事；且各家 CLI 官方文件已足夠，codify 的邊際價值低。與現有 `env-doctor` 亦有部分重疊。**不建議建立**，除非未來反覆在多台機器重裝或踩到 WSL 特有坑。
